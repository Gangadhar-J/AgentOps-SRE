# v0.8.0 — Event-Driven Investigations & Operator Experience

## 1. Overview & Vision

**AgentOps-SRE v0.8.0** evolves the platform from an interactive SRE console into an **event-driven autonomous incident investigation platform**.

In v0.8.0:
1. **Autonomous Investigation Triggering**: Ingests Prometheus Alertmanager webhook events, deduplicates firings, validates workload targets, applies storm cooldowns, and non-blockingly queues investigations.
2. **Durable Asynchronous Job Engine**: A thread-safe, SQLite-backed job store (WAL mode, busy timeout, atomic claims) that manages job lifecycles (`QUEUED`, `RUNNING`, `SUCCEEDED`, `FAILED`, `INCOMPLETE`, `CANCELLED`), lease renewal, dead worker recovery, and cooperative cancellation.
3. **Live SSE Progress Streaming**: Server-Sent Events endpoint (`/api/investigations/<job_id>/stream`) with monotonic event IDs, keep-alive heartbeats, terminal completion events, and `Last-Event-ID` reconnection resumption.
4. **Grafana Dashboard Embedding**: Secure kiosk iframe embedding and direct deep-linking with strict origin checking, query parameter sanitization, and automatic time range synchronization.
5. **Operator Email Notifications**: Formatted HTML and plain-text outcome emails delivered via SMTP with root cause summaries, confidence scores, and deep links to the Web UI and Grafana dashboards.
6. **Controlled Remediation Invariant**: Webhooks and workers can autonomously trigger investigations and root cause analysis, but **never** authorize remediation. All remediation actions strictly require human approval through the policy engine and security gateway.

## 3. Investigation Job Lifecycle & State Machine

Every investigation is tracked by an `InvestigationJob` persisted in `data/agentops.db`:

```text
                  ┌────────────┐
                  │   QUEUED   │
                  └─────┬──────┘
                        │ Worker claim (BEGIN IMMEDIATE)
                        ▼
                  ┌────────────┐     Cancellation     ┌────────────┐
                  │  RUNNING   │ ───────────────────> │ CANCELLED  │
                  └─────┬──────┘                      └────────────┘
                        │
         ┌──────────────┼──────────────┐
         │              │              │
         ▼              ▼              ▼
   ┌───────────┐  ┌───────────┐  ┌────────────┐
   │ SUCCEEDED │  │  FAILED   │  │ INCOMPLETE │
   └───────────┘  └───────────┘  └────────────┘
```

### Granular Investigation Stages
During the `RUNNING` state, the worker records granular progression events:
- `queued`: Job entered database queue.
- `starting`: Worker acquired lease and spawned execution thread.
- `collecting_kubernetes`: Querying pod health, container statuses, and warning events.
- `querying_prometheus`: Querying error rates, latency percentiles, and memory metrics.
- `querying_loki`: Querying recent error and panic log lines.
- `evidence_collected`: Multi-signal evidence items assembled and validated.
- `llm_inference_started`: Real LLM provider invoked with structured prompt.
- `llm_inference_completed`: Model output received, schema validated, and evidence grounded.
- `evaluating_policy`: Determining whether remediation is allowed, denied, or requires approval.
- `remediation_recommended`: Proposed remediation plan attached with approval ID.
- `completed`: Investigation finalized; terminal `IncidentReport` recorded.

## 4. Concurrency, Storage & Worker Leasing

1. **Storage Engine**: SQLite in WAL (`Write-Ahead Logging`) mode with a busy timeout of 5000ms.
2. **Atomic Lease Acquisition**: Workers use transactional `BEGIN IMMEDIATE` blocks to claim jobs (`UPDATE investigation_jobs SET status='RUNNING', worker_id=? WHERE job_id=? AND status='QUEUED'`).
3. **Dead Worker Recovery**: Active workers renew their `lease_expires_at` every 30 seconds. If a worker crashes or becomes unresponsive, expired leases are detected and the job is marked `FAILED` with a diagnostic message.
4. **Cooperative Cancellation**: When an operator issues `POST /api/investigations/<job_id>/cancel`, the job state transitions to `CANCELLED`. In-flight worker stages verify cancellation flags before expensive LLM calls, raising `InvestigationCancelledError`.
5. **Execution Models**:
   - **In-Process Worker** (`IN_PROCESS_WORKER=true`, default): Embedded background worker threads within the Flask web process for zero-configuration developer experience.
   - **Standalone Worker** (`make worker` / `agentops worker start`): Dedicated external worker process running independently for isolated concurrency.

## 5. Prometheus Alertmanager Ingestion & Deduplication

Alertmanager sends alert group notifications to `POST /api/v1/alerts`.

1. **Payload & Size Validation**: Request body is capped at 512 KB and validated against Alertmanager v4 JSON schema (`version="4"`, `status`, `alerts`, `commonLabels`, `groupLabels`).
2. **Workload Discovery**: Targets are identified from alert labels (`workload`, `deployment`, `app`, `container`, `job`) and namespace (`namespace`). Malformed or missing targets are rejected with `400 Bad Request`.
3. **Deduplication & Cooldown**:
   - Alert fingerprints (`alert.fingerprint` or SHA-256 of sorted label key-value pairs) are tracked in `alert_deduplication`.
   - Subsequent deliveries of an ongoing alert do not trigger duplicate investigations.
   - A configurable cooldown (`ALERT_COOLDOWN_SECONDS=300`) protects against alert storms.
4. **Resolved Alert Handling**: When `alert.status == "resolved"`, the resolution is recorded in `alert_deduplication` without triggering a new investigation.
5. **Shared Secret Authentication**: When `ALERTMANAGER_SECRET` is configured, webhooks must provide the secret via the `X-Alertmanager-Secret` header or `?secret=` query parameter.

## 6. Real-Time Server-Sent Events (SSE) Streaming

The SSE endpoint `GET /api/investigations/<job_id>/stream` provides efficient, low-overhead live progress updates:

1. **Monotonic Event IDs**: Every progress event has an integer `event_id` assigned by SQLite autoincrement.
2. **Resilient Reconnection**: Clients supply `Last-Event-ID` in request headers. The server queries only events where `event_id > last_id`, resuming the stream without dropped messages.
3. **Heartbeat Pings**: Periodic `: ping\n\n` comments keep HTTP connections alive across proxies and reverse proxies.
4. **Terminal Event**: Upon job completion or cancellation, a final `event: done\ndata: {"status": ...}\n\n` is sent and the stream cleanly closes.

## 7. Security Invariants & Human-in-the-Loop Governance

milestone v0.8.0 strictly preserves all security invariants established in v0.7.2:

1. **Zero Mock Fallback**: Live investigations strictly forbid fallback to mock RCA or deterministic generators. Real LLM failures produce transparent failure records.
2. **Investigation ≠ Remediation**: Incoming alerts or LLM diagnoses **never** authorize infrastructure changes.
3. **Capability Token Boundary**: Remediation actions must match granted agent capabilities and are guarded by single-use approval tokens.
4. **Pre- and Post-Verification**: Before executing any mutation, live cluster state is re-verified; after execution, rollout convergence and pod health are verified.
5. **Strict Origin & Input Sanitization**: Grafana dashboard URLs and Alertmanager webhooks enforce strict origin and character whitelisting to prevent SSRF and injection attacks.

## 8. Failure-Mode Hardening & Concurrency Guarantees

### Worker Recovery & Zombie Prevention
- **Active Heartbeat Thread**: While executing an investigation, a background thread periodically calls `renew_lease` every `JOB_LEASE_SECONDS / 3` seconds (e.g. 40s), preventing premature expiration during long LLM inferences.
- **Lease Loss Detection (`LostJobLeaseError`)**: If `renew_lease` returns `False` (lease expired and claimed by another worker), the active worker immediately aborts execution.
- **Zombie Worker Guard**: `complete_job` and `fail_job` enforce `worker_id` lease-ownership checks (`WHERE job_id = ? AND status IN ('RUNNING', 'QUEUED') AND (worker_id = ? OR worker_id IS NULL)`). A slow or paused zombie worker cannot overwrite the state of a reclaimed or completed job.
- **Bounded Lease Retries**: Unresponsive worker leases are retried up to `MAX_JOB_RETRIES` (default: 3). If a job repeatedly crashes workers, it transitions to `FAILED` with a `lease_exhausted` event instead of infinitely looping.

### Alertmanager Authentication & Deduplication
- **Constant-Time Verification**: Authenticates secrets using `hmac.compare_digest` to prevent timing side-channels.
- **Header-First Authentication**: Enforces HTTP headers (`Authorization: Bearer <secret>` or `X-Alertmanager-Secret: <secret>`). Query-string secret parameters (`?secret=`) are blocked by default (`ALERTMANAGER_ALLOW_QUERY_AUTH=false`) to prevent credential leakage into server access logs and monitoring traces.
- **Fingerprint-Aware Deduplication**: Uses `alert.fingerprint` alongside `alertname:namespace:workload` to ensure alerts for distinct containers or failure modes on the same workload are evaluated independently.
- **Resolved-to-Firing Freshness**: When an alert resolves (`status == "resolved"`), its active cooldown is cleared (`cooldown_until = NULL`). A subsequent firing transition is recognized as a new incident cycle and is never falsely suppressed by the previous cooldown.

### Notification Fault Isolation
- **SMTP Failure Isolation**: Outcome email delivery errors (`smtplib.SMTPException`, socket timeouts, network errors) are safely caught and logged. They **never** alter the terminal `JobStatus.SUCCEEDED` or `IncidentReport.status`.
- **Idempotent Single-Dispatch**: Atomically claims dispatch ownership via `UPDATE investigation_jobs SET notification_sent = 1 WHERE job_id = ? AND notification_sent = 0`, ensuring retried worker loops or concurrent completion attempts never produce duplicate emails.

### Benchmark Replay Quality Gate vs. Live Diagnostic Accuracy
- **Deterministic Replay (v0.6 Engine)**: The 96.5% benchmark score evaluates schema validity, tool boundaries, capability checks, and regression resistance against recorded fixtures under simulated conditions.
- **Live LLM Accuracy**: In production, diagnostic accuracy depends on real-time cluster telemetry fidelity, real LLM reasoning grounding, and model selection. Replay benchmarks must not be conflated with live diagnostic guarantees.
