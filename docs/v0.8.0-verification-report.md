## 3. Runtime, Workers, APIs, and Integrations (Checkpoint B)

A dedicated controlled runtime experiment suite (30 independent checks across 2 verification harnesses) was executed against the v0.8.0 engine.

### 3.1 Asynchronous Job Lifecycle & API Endpoints
- **Submission (`POST /api/incidents/investigate`):** Enqueues an investigation and immediately returns `202 Accepted` with durable `job_id` and initial status `QUEUED` (verified in `JOB-01`).
- **Result Polling While Pending (`GET /api/investigations/{job_id}/result`):** Correctly returns `409 Conflict` with `{"status": "pending", "job_status": "QUEUED"}` until the job reaches a terminal state (verified in `JOB-02`).
- **Terminal Result Retrieval (`GET /api/investigations/{job_id}/result`):** Returns `200 OK` with full `IncidentReport` payload containing diagnosis, root cause, confidence score, and remediation proposal once completed (verified in `JOB-05`).
- **Events Timeline (`GET /api/investigations/{job_id}/events`):** Monotonically ordered events returned with incremental integer event IDs, enabling clean pagination via `?after=<id>` (verified in `JOB-03`).
- **Server-Sent Events (`GET /api/investigations/{job_id}/stream`):** Delivers live SSE events (`event: investigation_queued`, `event: progress`, `event: done`) and respects `Last-Event-ID` resumption (verified in `JOB-04`).

### 3.2 Investigation Worker Engine & Lease Management
- **Atomic Job Claim (`WKR-01`):** 10 concurrent worker threads contended for a single queued job. Due to `BEGIN IMMEDIATE` transactional locking, exactly 1 worker claimed the job; 9 received empty queues with zero race conditions or double executions.
- **Heartbeat Lease Renewal (`WKR-02`):** Active workers running background heartbeats extend their `lease_expires_at` timestamp in SQLite, preventing healthy workers from being marked abandoned during long LLM inference.
- **Dead Worker Re-claim (`WKR-03`):** When a worker crashes or abandons a lease, a healthy worker safely re-claims the job after lease expiration, incrementing `retry_count` from 0 to 1.
- **Zombie Worker Protection (`WKR-04`):** If a worker loses its lease (due to network partition or freeze) and later attempts to write back results via `complete_job` or `fail_job`, the transaction checks `worker_id` and lease validity, safely rejecting the stale write (`return False`).
- **Lease Retry Limit Safe Failure (`WKR-05`):** When a job exceeds `MAX_JOB_RETRIES=3` due to repeated worker lease timeouts, it is not retried indefinitely; it transitions to `status: FAILED`, `stage: failed`, with an explicit `LeaseTimeoutError` recorded in `error_json`.
- **Cooperative Cancellation (`test_queued_job_safe_cancellation`, `test_cancellation_during_execution`):** Investigations can be cancelled while queued or during active execution, halting inference and preventing false success outcomes.

### 3.3 Prometheus Alertmanager Ingestion & Deduplication
- **Authentication Enforcement (`ALM-01`):**
  - Unauthenticated webhook requests rejected with `401 Unauthorized`.
  - Deprecated query-string token authentication (`?secret=...`) is **blocked by default** (`ALERTMANAGER_ALLOW_QUERY_AUTH=false`) to prevent secret leakage into HTTP proxy and server access logs.
  - Standard headers (`Authorization: Bearer <secret>` and `X-Alertmanager-Secret: <secret>`) authenticated in constant time using `hmac.compare_digest`.
- **Payload Limits & Target Validation (`ALM-02`, `ALM-05`):**
  - Webhook payloads exceeding 512 KB are rejected with `413 Request Entity Too Large`.
  - Malformed or malicious target namespaces/workloads (e.g. `rm -rf /` or path traversals) fail Kubernetes DNS-1123 naming validation and are rejected with `400 Bad Request`.
- **Deduplication & Cooldown Isolation (`ALM-03`, `ALM-04`):**
  - Deduplication key: `alertname:namespace:workload[:fingerprint]`.
  - Repeated webhook firings for an active investigation return `200 OK` (`status: deduplicated`) and increment `delivery_count` without launching duplicate jobs.
  - A burst of 10 simultaneous webhook deliveries resulted in exactly 1 accepted job and 9 deduplicated responses.
  - **Resolved-to-Firing Transitions:** When an alert resolves (`status: resolved`), `cooldown_until` is cleared (`NULL`). When the alert fires again, it immediately creates a brand-new investigation job, ensuring recurring incidents are never suppressed.

### 3.4 Grafana Integration & URL Sanitization
- **Catalog Endpoint (`GRAF-01`):** `GET /api/grafana/dashboards` returns registered dashboards (`cluster-overview`, `workload-detail`, `system-metrics`, `logs-explorer`) and reachability status.
- **URL Parameter Sanitization (`GRAF-02`):** Direct and embed URLs (`kiosk=tv`) validate namespaces and workloads against Kubernetes naming rules. Malformed inputs containing XSS probes or path traversals are rejected with `400 Bad Request`.

### 3.5 Operator Notification Safety & Idempotency
- **SMTP Failure Isolation (`NOTIF-01`):** If the SMTP server is down or times out during outcome notification dispatch, the exception is caught, logged, and recorded as a timeline event (`notification_failed`). The investigation outcome remains `SUCCEEDED` and is never falsely marked as failed.
- **Single-Send Idempotency Guard (`NOTIF-02`):** Database flag `notification_sent` is claimed atomically (`UPDATE ... SET notification_sent = 1 WHERE notification_sent = 0`). Subsequent attempts or retries return `False`, preventing duplicate emails.

## 4. Security Audit & Failure Injection (Checkpoint C)

### 4.1 Security Boundaries & Remediation Invariant
AgentOps-SRE enforces an uncompromising security boundary:
1. **Autonomous Investigations Only:** Alerts and webhooks trigger *investigations* and *root cause analysis*, never remediation.
2. **Strict Human-in-the-Loop (HITL):** Any remediation recommendation (restart, scale, rollback) produces an `ActionRequest` evaluated by the Policy Engine, yielding `REQUIRE_APPROVAL` (`SEC-01`).
3. **Remediation Allowlist:** Only 3 remediation actions exist in the capabilities taxonomy (`restart_deployment`, `scale_deployment`, `rollback_deployment`). All unauthorized capabilities (e.g. deleting pods, cluster role bindings) are rejected by default (`SEC-05`).

### 4.2 Security Gateway Protection Mechanisms
- **Tampered Request Binding (`SEC-02`):** When an operator approves an action request, the approval record binds a cryptographic hash of the action parameters, target resource, and evidence references. If an attacker tampers with the request (e.g., changing the target namespace from `demo` to `production`), the gateway detects the hash mismatch and denies execution (`Tampered Remediation Request Binding Rejection: PASS`).
- **Single-Use Approval Token Replay Prevention (`SEC-03`):** Once an approved action executes, the approval status is immediately transitioned to `CONSUMED`. Subsequent replay attempts with the same `approval_id` are blocked with `DENY` (`Approval request has already been consumed: PASS`).
- **Default-Deny Policy Enforcement (`SEC-04`):** Remediation attempts targeting unauthorized namespaces (e.g., `kube-system`) or unspecified resources are immediately rejected by the policy engine (`Default Deny: PASS`).

### 4.3 LLM & Evidence Grounding Boundary
- **Schema Validation:** LLM responses are parsed and validated against strict Pydantic schemas (`RootCauseAnalysis`, `IncidentReport`).
- **Evidence Hallucination Detection (`RCA-01`, `RCA-02`):** The `EvidenceEvaluator` verifies all `evidence_ids` cited by the RCA against the `InvestigationContext`. Valid evidence citations pass with scores $\ge 0.8$; ungrounded or fabricated citations (e.g., `E999`) trigger a critical failure, score $0.0$, and are rejected (`PASS`).

### 4.4 Failure Injection & Database Resilience
- **SQLite WAL Mode (`SQL-01`):** Database confirmed in `PRAGMA journal_mode=WAL` with a 30-second busy timeout.
- **High-Concurrency Multi-Threaded Ingestion (`SQL-02`):** 20 concurrent writer threads executed simultaneous job enqueues. All 20 succeeded with 0 lockouts, 0 database busy errors, and exact queue depth accounting.

## 7. Production Readiness Assessment & Recommendations

### 7.1 Architecture Strengths
1. **Durable, Dependency-Light Event Engine:** Operating on SQLite with WAL mode avoids operational complexity from Redis/Celery while delivering sub-millisecond atomic locking, worker heartbeat renewals, and crash recovery.
2. **Defensive Invariant Architecture:** The strict separation between autonomous investigation triggers (Alertmanager webhooks) and controlled remediation authorization (HITL approval gateway) ensures zero unauthorized cluster mutations.
3. **Observability Depth:** Monotonic timeline events combined with Server-Sent Events (SSE) and Grafana deep-links provide a transparent operator experience.

### 7.2 Operational Limitations & Deployment Prerequisites
1. **Local Kind Cluster Startup:** To run integration tests against real Kubernetes workloads, start the cluster via `make start` or `kind create cluster --config kubernetes/kind-config.yaml` before running `pytest tests/test_infrastructure.py`.
2. **Multi-Replica Deployment Consideration:** The SQLite job store relies on standard filesystem locks (`BEGIN IMMEDIATE` and WAL). When scaling to multiple server nodes, either run a single worker process with internal multi-threading or migrate `JobStore` to PostgreSQL using the existing repository abstraction.
3. **Alertmanager Ingress Security:** Ensure `/api/v1/alerts` is protected by `ALERTMANAGER_SECRET` in production and configured behind authenticated network ingress.
